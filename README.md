# jira-backlog-check

회의록의 할 일을 Jira에 만들기 전에 기존 백로그와 대조하고, 사람이 Confluence 검토 문서에서 확인한 것만 반영하는 도구입니다.

회의록을 이슈로 옮길 때 시간이 드는 것은 옮기기 전에 백로그를 뒤져 확인하는 일입니다. 이미 있는 일인지, 예전에 고친 버그가 다시 나온 것인지, 어느 에픽과 스토리 아래에 둘지를 후보마다 찾아 근거와 함께 보여 줍니다. 만들지, 기존 이슈에 합칠지, 다시 열지는 사람이 정합니다.

Jira Cloud, Confluence Cloud, Slack으로 동작하는 개인 프로젝트입니다.

## 동작 흐름

```
회의록 (Confluence, 라벨 '회의록')
   │ 사람이 페이지 상태를 '확인됨'으로 바꿈 → 자동화 규칙이 서버를 부름
   ▼
① 읽기        회의록 본문과 액션 아이템
② 추출 (AI)   이슈 후보, 근거 문장, 우선순위와 스프린트(회의록에 근거가 있을 때만)
③ 대조 (AI)   백로그 제목을 훑어 볼 이슈를 고른 뒤, 본문과 해결 기록을 읽고 중복, 재발, 관련을 판단
④ 검사 (코드) 인용한 문장이 회의록과 이슈 본문에 실제로 있는가, 없는 이슈 키, 제목 규칙, 이슈 구조, 빠진 액션 아이템
⑤ 검토 문서   회의록 아래에 Confluence 페이지로 만들고 Slack으로 알림
   │ 사람이 후보마다 체크(반영 여부)하고 결정, 제목, 상위, 설명을 고친 뒤 상태를 '확인됨'으로 바꿈
   ▼
⑥ 반영 전 검사 (코드)  하나라도 틀리면 아무것도 반영하지 않고 문서 맨 위에 고칠 곳을 표시
⑦ 반영        새로 만들기 / 합치기(기존 이슈에 댓글) / 다시 열기 / 만들지 않음, 관련 링크와 선행 링크
⑧ 결과        검토 문서를 결과 표로 바꾸고 Slack으로 알림. 검토하던 모습은 페이지 기록에 남음
```

## AI가 하는 일과 사람이 하는 일

| | 하는 일 |
|---|---|
| AI | 회의록에서 이슈 후보를 뽑고, 기존 이슈와의 관계(중복, 재발, 관련)와 제안(새로 만들기, 합치기, 다시 열기)을 근거 문장과 함께 낸다 |
| 코드 | AI가 인용한 문장이 회의록과 이슈 본문에 실제로 있는지, 이슈 구조와 제목 규칙이 맞는지, 빠진 액션 아이템이 없는지 검사한다. 과거 버그의 해결 기록은 AI가 옮겨 적지 않고 Jira에서 그대로 꺼내 보여 준다 |
| 사람 | 검토 문서에서 후보마다 반영 여부를 체크하고 결정, 제목, 상위, 설명을 고친다. 페이지 상태를 '확인됨'으로 바꿔야 Jira에 반영된다 |

검사에 걸렸거나 AI가 주의를 붙였거나 합치기, 다시 열기를 제안한 후보는 체크가 풀린 채로 보여 줍니다. 사람이 펼쳐 보고 체크해야 반영됩니다.

## 설치와 설정

### 준비물

- Python 3.12 이상, [uv](https://docs.astral.sh/uv/)
- Jira Cloud 프로젝트와 Confluence Cloud 스페이스 (Free 플랜에서 확인)
- 모델 호출 수단 하나: Claude Code 로그인, Codex CLI 로그인, Anthropic API 키 중 하나
- Jira 프로젝트에 있어야 하는 것: 에픽 1개 이상(후보를 에픽에 배정), 컴포넌트 1개 이상(직군 구분에 씀), 링크 유형 Relates와 Blocks

### 설치

```
uv tool install git+https://github.com/Gunheui/jira-backlog-check
```

### 설정과 확인

명령 이름은 `pm-agent`입니다. 작업 폴더를 하나 정하고 그 안에서 실행합니다. 설정(`.env`), 실행 결과(`runs/`), 팀 양식(`templates/`)이 이 폴더에 놓입니다.

```
pm-agent init     # 질문에 답하면 .env를 만들고 이슈 양식을 templates/로 복사
pm-agent check    # Jira, Confluence, Slack, 모델 연결과 스페이스 준비 상태 확인 (읽기만 함)
```

`check`는 에픽과 컴포넌트가 있는지, '확인됨' 상태가 스페이스에 있는지, 양식의 이슈 유형이 Jira에 있는지를 알려 줍니다. 설정 칸의 설명은 `pm_agent/env.example`에 있습니다.

### 손으로 돌려 보기

```
pm-agent analyze --page <회의록 페이지 ID>        # 후보 추출, 대조, 검사. 아무것도 쓰지 않음
pm-agent doc create --run runs/<결과 파일>         # Confluence에 검토 문서 생성
pm-agent doc apply --page <검토 문서 ID> --dry-run # 무엇이 반영될지만 출력
pm-agent doc apply --page <검토 문서 ID>           # Jira에 반영
```

### 자동 실행

1. 서버에서 `pm-agent serve`를 띄웁니다(127.0.0.1:8787). 앞에 HTTPS 프록시를 둡니다. Caddy라면 설정은 이것이 전부입니다

   ```
   your-domain.example {
       reverse_proxy 127.0.0.1:8787
   }
   ```

2. Confluence 스페이스 설정의 자동화에서 규칙 두 개를 만듭니다. 상태와 자동화 규칙은 API로 만들 수 없어 이 단계는 손으로 합니다

   | | 규칙 1: 회의록 → 검토 문서 | 규칙 2: 검토 문서 → Jira 반영 |
   |---|---|---|
   | 트리거 | 페이지 상태 변경 → '확인됨' | 페이지 상태 변경 → '확인됨' |
   | 조건 (CQL) | `label = "회의록"` | `label = "이슈검토"` |
   | 액션 | 웹 요청 보내기, POST `https://<서버>/hooks/meeting-published` | 웹 요청 보내기, POST `https://<서버>/hooks/review-done` |
   | 헤더 | `Content-Type: application/json`, `X-PM-Agent-Secret: <.env의 WEBHOOK_SECRET>` (숨김 체크) | 같음 |
   | 본문 | 사용자 지정 데이터 `{"page_id": "{{page.id}}"}` | 같음 |
   | 응답 기다리기 | 끔 | 끔 |

   헤더 칸에 회색으로 보이는 예시 글자는 입력된 값이 아닙니다. 한국어 화면에서는 예시가 번역돼 값처럼 보이니 영어로 직접 입력합니다.

3. 회의록 페이지에 `회의록` 라벨을 붙입니다. 회의가 끝나고 상태를 '확인됨'으로 바꾸면 규칙 1이 돕니다. `이슈검토` 라벨은 도구가 검토 문서를 만들 때 붙입니다

서버도 요청을 한 번 더 확인합니다. 비밀 헤더가 맞아야 하고, 회의록은 라벨이 있어야 하며, 검토 문서는 도구가 만든 문서여야 처리합니다. 자동화 규칙은 스페이스 관리자가 고칠 수 있어서, 조건이 빠지더라도 엉뚱한 페이지가 Jira에 쓰이지 않게 하려는 것입니다.

Confluence Free 플랜의 자동화는 조직 합산 월 50단계입니다. 회의록 1건을 끝까지 처리하는 데 7단계가 집계됐습니다. 유료 플랜은 사용자 수에 비례합니다.

### Slack 알림 (선택)

`slack-app-manifest.yaml`로 앱을 만들고 봇 토큰을 `.env`의 `SLACK_BOT_TOKEN`에 넣습니다. Slack은 알림만 맡습니다(검토 문서 준비, 반영 결과, 검사 오류, 실행 실패). 토큰을 비워 두면 알림 없이 동작합니다.

## 이슈 양식 바꾸기

AI가 이슈 제목과 설명을 쓸 때 따르는 양식은 작업 폴더의 `templates/` 안에 있는 글 파일입니다. `pm-agent init`이 기본 양식을 이 폴더로 복사해 주고, 파일을 고치면 다음 실행부터 바로 적용됩니다. 코드를 고칠 필요가 없습니다.

| 파일                                            | 내용                   |
| --------------------------------------------- | -------------------- |
| `rules.md`                                    | 모든 유형에 공통인 제목과 설명 규칙 |
| `story.md`, `task.md`, `bug.md`, `subtask.md` | 유형별로 언제 쓰는지와 설명 양식   |

파일은 두 부분으로 나뉩니다. 맨 위 `---` 사이의 설정은 코드가 검사에 쓰고, 그 아래 본문은 그대로 AI에게 줍니다.

```
---
issue_types: 버그
required_sections: 실제 결과, 기대 결과
---
# 버그

언제 쓰나: 동작이 기대와 다른 문제. 제목 앞에 영역 머리말을 붙인다.
(이하 설명 양식)
```

| 설정                   | 파일         | 뜻                                                                            |
| -------------------- | ---------- | ---------------------------------------------------------------------------- |
| `issue_types`        | 유형별 파일     | 이 양식을 쓰는 Jira 이슈 유형 이름. Jira 프로젝트에 있는 이름을 그대로 적는다(영어 Jira면 Story, Task, Bug) |
| `required_sections`  | 유형별 파일     | 설명에 꼭 있어야 하는 칸. 없으면 검사 오류로 표시                                                |
| `needs_assignee`     | 유형별 파일     | `no`로 두면 회의록에 담당이 없어도 확인 요청으로 올리지 않는다(스토리처럼 여러 작업을 묶는 유형)                    |
| `title_max_length`   | `rules.md` | 제목 글자 수 기준                                                                   |
| `title_forbidden`    | `rules.md` | 제목에 쓰지 않을 기호                                                                 |
| `bug_title_prefixes` | `rules.md` | 버그 제목 앞에 붙이는 영역 머리말 목록. 기본값은 예시이니 팀의 영역 이름으로 바꾼다                             |

유형을 더하려면 같은 모양의 파일을 하나 더 만들면 됩니다. AI는 양식 파일이 있고 Jira 프로젝트에도 있는 유형만 고릅니다.

이슈 유형은 이름이 아니라 Jira 계층(에픽, 일반, 하위 작업)으로 구분하므로 유형 이름이 달라도 동작합니다. 버그 유형 이름이 '버그'나 'Bug'가 아니면 `.env`의 `BUG_ISSUE_TYPE`에 적습니다. 양식 폴더를 다른 곳에 두려면 `.env`의 `TEMPLATE_DIR`로 지정합니다.
